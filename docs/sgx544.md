# SGX544MP1 (MediaTek MT5398, LG NetCast 4.x)

A fact sheet for the PowerVR SGX544 in this TV, in the format of powervr_sgx's
`docs/porting/cores/` (one fact, one tag). It's for bringing the core up under the mainline
kernel and, later, for adding it to powervr_sgx. Nothing here comes from closed userspace or
firmware contents. The LG kernel module is used only for its addresses and register writes.

| Tag | Meaning |
|---|---|
| **K** | GPL kernel-side DDK headers (`powervr_sgx/kernel/src/services4/srvkm/hwdefs/`: `sgx544defs.h`, `sgxmpdefs.h`, `sgxfeaturedefs.h`, `include/sgx_mkif_km.h`) |
| **B** | LG's shipped `pvrsrvkm.ko` (DDK `1.9@2291151`, build `cobra_lg_linux`, unstripped): disassembly of `SysLocateDevices`, `SysInitialise`, `SGXReset` |
| **S** | Read on this TV under the stock kernel (phase 0, 2026-11-23) |
| **C** | Confirmed under the mainline kernel with `mt5398_sgx` (`id`, boot 11, 2026-11-23) |
| **U** | Unknown |

## Identity

| Fact | Value | Tag |
|---|---|---|
| Core | SGX544, MP configuration, one core (MP1) | S, B |
| Register window | `0xf0040000`, `0xc000` long | B |
| Interrupt | GIC 85 = SPI 53 = BIM MISC bank line 21 (MediaTek calls the line `VECTOR_GFX3D_GP`) | B |
| Core clock | 324 MHz (`SysInitialise` stores `0x134fd900`) | B |
| `CORE_ID` (core 0, `0xf0048020`) | `0x01191101`: ID `0x0119` (SGX544), config multi=1, cores field 1, SLC field 1 | S |
| `CORE_REVISION` (core 0, `0xf0048024`) | `0x00010105` = 1.1.5. TI's builds only cover revs 116/117 | S |
| `MASTER_CORE_ID` / `MASTER_CORE_REVISION` | `0x4010` / `0x4014`: `0x01191101` / `0x00010105`, the same as core 0 | K, C |
| State after the warm boot (`id`, boot 11) | master and core 0 `SOFT_RESET` 0, `CLKGATECTL` `0x002aaaaa` (all modules auto), `CLKGATESTATUS` 0 (every module idle), `EVENT_HOST_ENABLE` 0, `EVENT_STATUS` `0x243c2780` (stale latches), `BIF_CTRL` 0. CKGEN `0x3d4` = 9, `0x3d8` = 1 as LG writes them. Register reads don't hang the bus | C |

## Register banks

| Bank | Offset | What | Tag |
|---|---|---|---|
| 0 | `0x0000` | Broadcast to the cores (LG's `SGXReset` writes core registers such as `BIF_CTRL` `0xc00` here) | K, B |
| 1 | `0x4000` | Master (`EUR_CR_MASTER_*` offsets already include it) | K |
| 2 + n | `0x8000` + n x `0x4000` | Core n. Only core 0 fits in the `0xc000` window | K, B |

The bank size is 16 KB (`SGX_REG_BANK_SHIFT` 14, base index 2, master index 1).
Core-bank offsets are the SGX544's own: `CLKGATECTL` 0x0, `CLKGATESTATUS` 0x8,
`CLKGATECTLOVR` 0xc, `CORE_ID` 0x20, `CORE_REVISION` 0x24, `SOFT_RESET` 0x80,
`EVENT_STATUS` 0x12c, `EVENT_HOST_ENABLE` 0x130, `EVENT_KICK2` 0xac0, `BIF_CTRL` 0xc00,
`BIF_INT_STAT` 0xc04, `BIF_FAULT` 0xc08, `BIF_DIR_LIST_BASE0` 0xc84 (K). Several of these
differ from the SGX545, whose `CORE_ID` is at 0x1c.

## Features (K, `sgxfeaturedefs.h`, SGX544)

32-bit device address space, multiple memory contexts with **8** BIF directory lists (the
SGX545 has 16), 4 USE pipes, auto clock gating, monolithic microkernel, multi event kick,
extended perf counters. The instruction set is **USSE2**, so powervr_sgx's assembler,
open microkernel and NIR compiler, which are USSE (SGX545) only, can't target it yet.

## Platform glue (B)

- `SysInitialise`, after the device is initialised: map CKGEN `0xf000d000`, write
  `+0x3d4` = 9 and `+0x3d8` = 1. The core already answers before these writes, so they
  aren't what powers it. Meaning U. `mt5398_sgx` reads them and never writes them.
- The MTK power hooks (`SysDevicePrePowerState` and friends) do nothing that matters for
  register access. The warm boot leaves the clocks as the stock kernel had them.

## Reset sequence (B, `SGXReset`, normal path)

1. `MASTER_SOFT_RESET` (`0x4080`) = `0x1ff`: core resets 0-3, IPF, DPM, VDM, SLC, BIF.
   Hardware recovery adds MCI: `0x3ff`.
2. Wait 100 core clocks.
3. `MASTER_BIF_CTRL` (`0x4c00`) = 0, `MASTER_SLC_CTRL` (`0x4d00`) = `0x4c000`,
   `MASTER_SLC_CTRL_BYPASS` (`0x4d04`) = `0x04000000`. Wait.
4. `MASTER_SOFT_RESET` = 0. Wait.
5. Clock gating (`CLKGATECTL` 0x0 and 0x4 in bank 0, values from the device info), then
   BIF setup in bank 0: `BIF_CTRL` 0, `0xc74`/`0xc78` 0, `BIF_DIR_LIST_BASE0` 0, ...
   `mt5398_sgx` stops after step 4.

## Under the mainline kernel

`src/mainline/kernel/drivers/misc/mt5398_sgx.c` binds `"mediatek,mt5398-sgx",
"img,powervr-sgx544"` and maps the window. At boot it touches nothing. On a write to
`/sys/bus/platform/devices/f0040000.gpu/action`:

| Action | Does |
|---|---|
| `id` | Reads CKGEN, the master ID/revision/soft reset, and core 0's ID, revision, clock gating, soft reset, event status/enable and `BIF_CTRL`. No writes |
| `reset` | Steps 1-4 above, then `id` |
| `park` | `MASTER_SOFT_RESET` = `0x1ff` and leave it there (the GPU can't fetch or write memory) |

`cat .../report` repeats the last result. The initramfs runs the action named in
`<stick>/netcast/mainline/sgx`, but only once the watchdog is armed. If a read hangs the
bus, the watchdog resets the TV to stock, and the ramoops log shows how far it got.

## Open questions

- ~~Is the stock microkernel still running after the warm boot?~~ **Yes** (2026-11-24): its 1 kHz timer task keeps
  incrementing `SGXMKIF_HOST_CTL.ui32TimeWraps` in RAM Linux has reused (FINDINGS.md "RAM corruption"). Boot 11's `id`
  (clocks gated, host events disabled) only showed it idle at that instant. Since 2026-11-24 nckexec holds the GPU in reset (`MASTER_SOFT_RESET` 0x1ff) before the jump, so
  the core is in reset when Linux starts.
- Whether the cores field (1) encodes 1 core or 2.
- What CKGEN `0x3d4` = 9 / `0x3d8` = 1 select.
- The stages past the reset (microkernel, USSE2) are U for the open stack.
- With nckexec holding the GPU in reset (2026-11-24), core-bank registers abort the bus until the reset is released. Only the
  master bank is readable. `SysReleaseReset()` (our pvrsrvkm) does LG's reset steps first. The `id` action of `mt5398_sgx` reads
  core registers, so don't run it on such a boot until it checks `MASTER_SOFT_RESET`.

## The DDK 1.9 driver under the mainline kernel (route A, 2026-11-23)

The open stack can't drive this core yet (USSE2), so the first 3D path is IMG's own: the
services kernel module from TI's open release of DDK 1.9 (tag
`TI_LINUX_OMAP_SGX_DDK_1.9_2253347`, Dual MIT/GPLv2), made to match LG's build and
ported to Linux 6.12, under the TV's own userspace (DDK `1.9@2291151`, soft-float, copied
from the TV by `fire.sh`, never shipped). `third_party/build-sgx.sh` builds it. The changes
to TI's files are `src/mainline/sgx/patches/`, our files are the rest of `src/mainline/sgx/`.

What has to match LG's `pvrsrvkm.ko`, and how it was checked (host first, then on the TV: on 2026-11-24 `pvrsrvinit` exits 0 and `sgxgltest` passes):

TI-only additions removed (patch 0001): `PVRSRV_MISC_INFO` cache-op regions and the
`CUSTOM_*`/`*_REGIONS` cache ops, the three bridge commands above, `pfnSwapToDCSystem` in
the display-class jump table. Linux 6.12 port (patch 0002): vmalloc with pgprot via `vmap`,
`vm_flags_set`, `vmf_insert_mixed`, `timer_setup`, `follow_pfnmap_start`, the new
`get_user_pages`/`access_ok`, ARM cache ranges via `__cpuc_flush_dcache_area` + `outer_cache`,
a DT platform driver, no `/proc/pvr`. MISR is a tasklet and timers are kernel timers, as in
LG's build: the workqueue mode needs `CONFIG_PREEMPT`.

Userspace: LG's EGL loads `libpvrPVR2D_CobraNetCast40WSEGL.so` (needs LG's `libUMA.so`)
and falls back to `libpvrEWS_NullWSEGL.so`. It ignores a `WindowSystem` hint in
`/etc/powervr.ini`. LG's `libpvrPVR2D_NullWSEGL.so` rejects every display. So our WSEGL
(`src/mainline/sgx/wsegl/`, interface version 2: 14 functions, caps `{type, value}`, 8-word
configs, 11-word drawable params) goes in under the fallback name. Stage 1 is pbuffers only.
Under qemu-arm with Debian's armel glibc 2.41, LG's EGL/GLES2 load, take our WSEGL and stop
at opening `/dev/pvrsrvkm`, as expected off the TV.

Test on the TV (`src/mainline/sgx/pvrtest.sh`, run by `netcast-pvr.service` when
`<stick>/netcast/mainline/pvrtest` exists, or by hand): unbind `mt5398-sgx`, insmod, run
LG's `pvrsrvinit` (loads the microkernel: the first time the GPU executes code under
mainline), then `sgxgltest` (pbuffer clear, a shaded triangle, `glReadPixels`, a timed
loop, `frame.ppm`). Needs a kernel with `CONFIG_MODULES=y`.

## Drawing to the panel with the GPU (design 2026-11-24, step 0 done, see the end)

The GPU can render off-screen (`sgxgltest` PASS). Reading a frame back takes ~255 ms, so the panel must scan out memory
the GPU rendered into. No kernel change is needed for a first version: the buffers come from our KMS driver and the GPU wraps them.

**LG's own design** (disassembly of `libpvrPVR2D_CobraNetCast40WSEGL.so`, sources B): the window's buffers are mmapped framebuffer memory, each
`PVR2DMemWrap`ped. `WSEGL_SwapDrawable` hands the buffer to a worker thread, which calls `PVR2DQueryBlitsComplete(wait)` and
then flips with an `ioctl`. `WSEGL_GetDrawableParameters` fills 11 words: 0 width, 1 height, 2 stride in pixels (rounded up to 32),
3 pixel format, 4 CPU address, 5 GPU address, 6 client meminfo pointer, 9 and 10 extra (swap interval, flags, zero at first).
"Source" params are the previous buffer, "render" the current one. Function order in the table:
IsDisplayValid, InitialiseDisplay, CloseDisplay, CreateWindowDrawable, CreatePixmapDrawable, DeleteDrawable, SwapDrawable,
SwapControlInterval, WaitNative, CopyFromDrawable, CopyFromPBuffer, GetDrawableParameters, ConnectDrawable, DisconnectDrawable.

**What we can't reuse:** `libpvr2d.so`. `PVR2DCreateDeviceContext` ends in `PVRSRVOpenDCDevice`, and our kernel registers no display class
(dc_cobra's job). Its wrap call is one call to `libsrv_um`, whose arguments are known from it:
`PVRSRVWrapExtMemory(devdata, hDevMemContext, bytes, pageoffset 0, contig flag, NULL, linaddr, flags 0, &meminfo)` after `PVRSRVConnect`, `EnumerateDevices`,
`AcquireDeviceData`, `CreateDeviceMemContext`. So our WSEGL links `libsrv_um` directly.

**Path (stage 0/1):** open pvrsrvkm, then `/dev/dri/card0` (in this order: the kernel closes fds in ascending order at exit, so the wraps go before the buffers), then 2-3 dumb
buffers (1920x1080, pitch 7680 = 1920 px, a multiple of 32), mmap, wrap each. Kernel side (read in our port, not yet run): the DRM mapping is `remap_pfn_range` (VM_IO|VM_PFNMAP|VM_DONTEXPAND|VM_DONTDUMP), which is
what `OSAcquirePhysPageAddr` accepts after get_user_pages refuses it. `follow_pfnmap_start` gets the pfns and takes page references.
Hazards: the wrap holds `get_page()` on CMA pages, so a buffer must be unwrapped before its GEM object is destroyed.
The GPU uses 32-bit addresses and the scanout pool is in 0x10000000-0x1fffffff (fine).
Pixel format: OSD ARGB8888 is the same byte order as the DDK's 8888 (ARGB), to be confirmed by a readback of a known colour.

**Waiting for the GPU:** `PVR2DQueryBlitsComplete` polls the client sync data, but LG's build has `PVRSRV_DISABLE_UM_SYNCOBJ_MAPPINGS`,
so that pointer may be NULL in userspace (the function then fails at once, and LG's worker ignores the result: unconfirmed). Use the bridge calls instead: `PVRSRVSyncOpsTakeToken` /
`PVRSRVSyncOpsFlushToToken(wait)`, exported by `libsrv_um` and independent of the mapping. Then `drmModePageFlip` (raw ioctl) and wait for its event (vblank is our 60 Hz timer).

**Native window:** our own struct (DRM fd, size, buffers, swap callback), so the same WSEGL serves a test program now and a small libgbm shim later.

**Steps**
0. `sgxscan` (armel): dumb buffer + wrap + render + SyncOps wait, checked through the CPU mapping. Creates dumb buffers without DRM master, so the desktop keeps running and the panel
   is not touched. Answers: does the wrap work, is stride/format right, is the memory up to date when SyncOps says so (SLC write-back).
1. Page flips: a spinning frame on the panel at 60 fps. Needs DRM master, so lightdm/Xorg stops for the test.
2. Upload speed: `glTexImage2D` of a full 1080p frame from CPU memory (decides whether a GPU desktop is practical).
3. Desktop, depending on 2. Constraint: LG's libraries are soft-float armel. Debian's desktop is armhf (its float arguments are passed differently), so an armhf compositor cannot load
   them. Compositor and GL applications must be armel builds (multiarch armel is already in the image), but armhf programs can still talk to an armel Wayland compositor, because that is a socket protocol.
   Weston's gl-renderer on LG's EGL 1.4 would need a libgbm shim plus the extensions it expects (unchecked). Xorg glamor and Mesa GBM are not options on this EGL.

**Step 0 result (2026-11-24, on the TV, pvrsrvkm 93ff4fe9, Xorg running, panel untouched): PASS, first run.** `sgxscan` + the new WSEGL
(`netcast_window.h`): two 1920x1080 dumb buffers wrapped with `PVRSRVWrapExtMemory` (GPU addresses 0x100a0000, 0x10889000), six solid frames alternating buffers correct at
the corners, centre and every pixel of the last. Triangle right way up (GL's bottom-left origin is the buffer's bottom row). ARGB8888 byte order right. Stride 1920.
The SyncOps wait is real: 20 blended layers read back right at once with the wait, 0 (stale) without it and right 200 ms later. 100 simple 1080p frames, each waited
for: 230-250 fps (4.0-4.3 ms). sync->data is not NULL in userspace (so PVR2DQueryBlitsComplete would have worked too). No kernel messages, 300 MB scan 0 hits, CMA returned.

**Step 1 result (2026-11-24, on the TV): PASS.** `sgxflip`: three GPU-rendered 1920x1080 XRGB8888 buffers page-flipped on the panel with lightdm stopped
(`/dev/shm/flip.sh` restarts it on exit). 3000 frames in 60 s: 3000 flips, all confirmed by the header mirror, none timed out. The user saw the colour chart
(order, edges and corners), a tear-free moving bar and a clean spinning triangle as expected. `PAGE_FLIP` right after `SETCRTC` returns EBUSY for a few ms (retried).
**The flip rate is 50/s, not 60** (interval average 20.05 ms: four of 16.7 ms then one of 33.3 ms, i.e. our 60 Hz vblank timer against a 50 Hz latch). So the panel
appears to refresh at 50 Hz while `mt5398_osd` assumes 60 (confirmed below). GPU cost was far under budget (~4 ms a frame).
Fix idea: derive the timer period from the mirror (or a 1080p50 mode), so flips don't beat.

**Panel rate (2026-11-24, reads only).** `sgxflip -m` timestamps the OSD's header mirror (0xf0021324): 600 of 600 changes 20.05 ms apart (max 20.06), one per GPU frame.
The post-scaler block (PSC) holds the output timing: 0xf005e30c = `0x08980546` (HTOTAL 2200, VTOTAL 1350, measured 0xf005e3a8 = 1349), at DCLK 148.5 MHz
(DDDS CW 0x045D1745 = 48/11, SYSPLL 648 MHz): 148.5 MHz / (2200 x 1350) = 50.0 Hz. (SCPIP's 0xf002530c reads 1125, and that is not the output.) LG's 1080p panel tables give 2200 x 1125 at 60 Hz and
2200 x 1350 at 50 Hz with the same clock, so 60 Hz = VTOTAL 1125 (and front porch). LG picks it from what it is showing:
boot 15 recorded flips at 60 Hz, today (LG's layer on plane 2) 50. `vDrvSetLCDTiming_SETDATA()` sets HTOTAL/VTOTAL, front/back porches, ISR lines, so a Linux-side switch
is not one write. Try first: read 0xf005e30c on stock (memscan -d), put LG's UI on a screen where it reads 0x...0465, and fire from there.

**60 Hz boot (2026-11-24):** on stock, `memscan -d 0xf005e30c` read 1350 until the user changed screens, then 1125. The jump was fired from `/tmp` while it read 1125 (register re-read just before the jump).
Debian came up with PSC 2200x1125 (0xf005e30c = 0x08980465), so the panel mode survives the jump and depends on LG's state. Which screen did it isn't recorded yet.
`sgxflip -t 20 -m`: 59.75 fps, hardware latch every 16.71 ms (59.85 Hz), 3577 of 3588 intervals under 25 ms. 11 longer (one late frame per ~5 s), and 6-8 flip intervals over 20 ms per 20 s:
our 60.000 Hz software vblank timer drifts against the ~59.85 Hz panel, so now and then an event comes a tick late. At 50 Hz (same timer) there were none. Fix: pace the timer on the real latch (kernel change). Second run, watched: the user found 60 Hz a little smoother than 50 but with a few stutters, 50 perfectly smooth.

**Raster counter (2026-11-24, read-only):** 0xf005e380 (PSCSYS_20) is live: low half = current line (V), high half = H. Sampling its wraps for 5 s: 59.844 Hz (16.7102 ms, +-6 us jitter)
in the 60 Hz mode. So `mt5398_osd` can be phase-locked to the real refresh: at each timer tick read the line, re-arm the timer for the next vblank start, and take the period from HTOTAL x VTOTAL
(0xf005e30c) instead of the fixed 60.000. That removes the stutter (60.000 Hz timer vs 59.844 Hz panel) and reports the true rate (50 or 60).

**Driver fix (2026-11-24, built, NOT booted):** `mt5398_osd` now reads the panel raster (DTS `reg` gained "raster" 0xf005e300 and "route" 0xf0027804): mode 2200x1125 or 2200x1350 reported
as 60 or 50 Hz, the vblank tick re-armed for a line of the live counter (measured frame time, 100 ms at probe), and the latch line learnt from the first 8 flips (mirror polled every 100 us) so
vblank sits right after the OSD's header fetch. Falls back to the fixed 60 Hz timer if PSC isn't routed, totals are implausible or the counter doesn't move. `flip_stats` in sysfs shows the raster,
the tick line and the samples. Image 32185a05 (#38), DTB 6eb5555c (**both must be installed together**: an old DTB has no raster regs, so the driver falls back), `dist/netcast-vsync-update.zip`.
Offline check of the arithmetic: frame-time error < 0.02 %, tick falls within 1 line.

**Driver fix verified on the TV (2026-11-24, Image 32185a05 #38 + DTB 6eb5555c, booted from the stick at 60 Hz):** dmesg "panel raster 2200 x 1125, 60 Hz mode, frame 16711.388 us".
`sgxflip -t 20 -m`: 59.85 fps (1197-1198 frames per 20 s scene), no flip interval over 20 ms in any scene (average 16.71 ms, max 17.2), 3595 latches of which 2 long, both before the latch line was learnt
(tick at line 30 after 8 samples, 3607 flips latched, 0 timeouts). Before the fix: 6-8 late frames per scene. The user saw smooth motion with no stutters. Not tested: the 50 Hz path of the new driver.
**What makes LG's panel 60 Hz: the My Photos app** (or a photo inside it), per the user, who can repeat it. HOME reads 50. Which LG screens give 60 is otherwise unknown.

**Choosing the rate before the jump (2026-11-24, `src/tools/ncrate.c`, from disassembly, then tested on the TV, below).** LG's media player does it on purpose: `UI_EMF_Play` (RELEASE 0x73c560) calls
`API_VIDEO_SetFrameRate(1, 60)` -> `DDI_VIDEO_SetFrameRate` -> `VIDEO_SOC_SetFrameRate(on, rate)` (libmtk5398) -> `MTPMX_PANEL_ForceFrameRate(rate, 0 = release)` (libmtal) -> `/dev/mtal` ioctl **0x40040d29, rate by value**
-> `vDrvForceFrameRate()` (dtv_driver_adpt.ko) -> `vDDDSLCDSetting()` -> `vDrvLCDFreqSet()`. The driver keeps the force in `_bForceFrameRate`. Every path that recomputes the rate from the signal goes through
`vDDDSLCDSetting()`, which honours it. Totals are written from the vsync ISR (`vVdoOutISRCheckSetDataTrigger`, every 3rd interrupt). `MTPMX_PANEL_GetFrameRate` (0x40040d07, u32 *) reads the driver's rate.
Other callers in RELEASE: `MENU_CreateInputBlockWin` forces whatever rate is current (the likely reason HOME stays at 50), `VIDEO_PeriodicTask` only acts on an analog TV signal change, `API_VIDEO_SetInputSource` only on OLED sets.
Catch: `vDrvLCDFreqSet()` calls `OSD_PLA_Mute()` (plane +8 bits 15:8, fade, to 0 on all planes, restored by `vScpipNormProc` after 10 vsyncs), and neither nckexec's in-place path nor `mt5398_osd` rewrites that register: a jump
within those ~200 ms would boot to a black screen. `ncrate` waits for the rate measured on the line counter in two windows (0.8 s) and for the fade to be back. `fire.sh go` runs it after the splash, and puts the old rate back if nckexec refuses.
**Tested on the TV (2026-11-24).** `ncrate 60` from HOME at 50.00 Hz: 2200 x 1125, 59.9-60.0 Hz in 1.3 s, every time (10 or more switches), kept across the HOME key and a splash app coming and going, fades back to ff.
Forced 50 runs at **51.43** Hz (the force turns on the "good dclk" loop, `vDrvSetMTKGoodDclk`, which follows the absent video input), outside `mt5398_osd`'s 2% check. A bare release (rate 0) leaves **48** Hz (2200 x 1406).
The plain `MTPMX_PANEL_SetFrameRate` (0x40040d06) after a release gives 50.00, so `ncrate 50` and `ncrate release 50` end there. `fire.sh go` from HOME, layer on plane 2 (own-header path): Debian came up with
"panel raster 2200 x 1125, 60 Hz mode, frame 16726.572 us". The line counter then read 59.784 Hz in six 5 s windows over a minute, all equal. Plane 3 blend 0001ffff. Not tested: a boot with NETCAST_HZ=50, the in-place (plane 3) path,
a live TV or HDMI source, and fire.sh's undo on the TV (simulated, though `release 50` itself is tested).

**Step 2 result: upload speed (2026-11-24, `sgxupload`, kernel #38, every upload checked by a pixel readback).** TexSubImage2D 1080p RGBA or BGRA 24.0 ms call, 24.5 ms with draw + read (338 MB/s). TexImage2D (re-allocating)
29.2 ms, 55 ms total. 1080p RGB565 12.0 ms, 720p RGBA 10.5 ms, 512x512 3.5 ms, 256x256 0.8 ms, 64x64 0.4 ms. CPU side: memcpy cached -> WC screen buffer 12.6 ms per 1080p frame (657 MB/s), memset to WC 3.8 ms,
cached -> cached memcpy 14.2 ms (584 MB/s), WC -> cached 40 ms (208 MB/s: never read screen buffers with the CPU). GL has GL_OES_EGL_image, GL_IMG_texture_stream2, BGRA8888 (EXT and IMG), npot.
**Reading:** a full 1080p frame can't be uploaded each refresh (24 ms vs 16.7 at 60 Hz, 20 at 50 Hz). Partial updates can (a 512x512 damage costs ~3.5 ms). The copy into a screen buffer costs half as much as a GPU upload,
so a GPU-composited desktop would be slower than a CPU one for full-screen changes unless buffers are shared without copying (EGLImage from a mapped buffer, untested). Good fits for the GPU: full-screen GL programs and scaling or blending content that is already in textures.
